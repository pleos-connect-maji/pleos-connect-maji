# 맞이 상태 복원과 백그라운드 동작 설계 (#26)

> 상태: **초안 (팀 결정 필요)** · 담당: C(윤우린) · 관련: #26, #22, #24
> 이 문서는 코드를 바꾸지 않습니다. 저장 방식과 백그라운드 방식을 팀이 고르도록 옵션을 정리합니다.

## 1. 지금 상태

- 맞이 상태(`MajiFlowImpl`의 단계, 탑승자, 원래 상태, 준비 값, 바뀐 값)는 **메모리에만** 있습니다.
- 앱을 완전히 끄면(프로세스 종료) 상태가 모두 사라지고, 다시 켜면 `IDLE`입니다.
- 신호 구독은 `MainActivity`의 `DisposableEffect`에서 시작하고, 화면이 사라질 때 멈춥니다. 즉 **앱 화면이 살아 있는 동안만** 신호를 받습니다.

## 2. 해야 할 일 (#26 체크리스트)

| 항목 | 상태 | 비고 |
|---|---|---|
| 시트 이동 중 문 열림 → 시트만 정지, 준비는 계속 | 로직은 있음 | `stopSeat`만 부르고 준비 흐름은 그대로. 확인 테스트 필요 |
| 맞이 취소 → 원래 상태 복구 | 구현됨 | `cancel` → `restore` (테스트 있음) |
| 앱을 다시 켜면 진행 단계 복원 | **미구현** | 이 문서의 핵심 |
| 화면이 없어도 동작하는 백그라운드 서비스 | **미구현** | 이 문서의 2번 |

## 3. 복원 설계 (앱 재시작)

### 저장할 것
- 단계(`MajiStep`), 탑승자 id
- 원래 상태(`PassengerState`): 열선, 온도, 창문
- 준비할 때 보낸 값(`Climate`): 학습의 기준
- 탑승 뒤 바뀐 값(열선, 온도): 학습 후보
- 저장 시각(오래된 맞이는 버리는 기준에 사용)

### 저장 시점
- 단계가 바뀔 때마다 (`moveTo`), 원래 상태를 읽은 직후, 바뀐 값이 생길 때

### 복원 규칙 (안전 우선)
1. 앱을 켜면 저장된 맞이가 있는지 확인합니다.
2. 있으면 **단계, 탑승자, 원래 상태를 되살리고 진행 화면을 보여 줍니다.**
3. 신호 구독을 다시 시작한 뒤, 차의 현재 상태(기어, 문)를 받아서 단계를 맞춥니다. 저장된 단계와 현재 상태가 다르면 **현재 상태를 우선**합니다.
4. 되살린 맞이는 **최종 하차 또는 맞이 취소로 끝낼 수 있어야** 합니다. 원래 상태로 되돌리는 것이 목적이기 때문입니다.
   - 예: 준비 중에 앱이 꺼졌다면, 시트는 이미 움직였을 수 있습니다. 다시 켰을 때 취소를 누르면 저장된 원래 상태로 돌아갑니다.
5. 저장된 맞이가 오래되었으면(예: 하루 이상) 복원하지 않고 버립니다. 이 기준은 팀이 정합니다.

### 복원하지 않는 것
- 음성 재생(인사, 안내음) 중이던 것은 다시 재생하지 않습니다.
- 학습 저장은 최종 하차에서만 하므로, 복원 전에 확정하지 않은 값은 잃을 수 있습니다. 이는 허용 범위로 봅니다.

### 저장 방식 (팀 결정)

| 방식 | 장점 | 단점 |
|---|---|---|
| **DataStore(Preferences)** | 단순한 키-값 저장, 추가 설정 적음 | 복잡한 구조(원래 상태 묶음)는 JSON 문자열로 저장해야 함 |
| **Room 테이블** | 탑승자 DB와 같은 방식, 구조가 명확 | 테이블과 마이그레이션 추가 |

**추천**: DataStore에 맞이 한 건을 JSON 하나로 저장. 맞이는 한 번에 하나만 있으므로 단순한 방식으로 충분합니다.

## 4. 백그라운드 동작 설계

### 문제
- 지금은 앱 화면이 사라지면 신호 구독도 멈춥니다.
- 맞이 중에 사용자가 다른 앱(지도, 음악 등)을 쓰면 앱이 뒤로 가고, 그 사이 **P단 해제, 문 열림** 같은 신호를 놓칩니다.
- 놓치면 귀갓길 설정이나 인사가 실행되지 않습니다. 특히 최종 하차 후 원래 상태 복구가 실행되지 않을 수 있습니다.

### 옵션

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 포그라운드 서비스** | 알림을 띄우는 서비스가 흐름과 신호 구독을 맡음 | 앱 화면이 없어도 계속 동작. 시스템이 덜 죽임 | 알림 표시, manifest와 권한 설정, 팀 빌드 설정 변경 필요 |
| **B. 현재 방식 유지** | 화면이 살아 있을 때만 동작 | 가장 단순 | 다른 앱을 쓰면 신호를 놓침 |
| **C. 플랫폼 기능 활용** | 차 플랫폼이 백그라운드 신호를 주는지 확인 | 코드 변경 최소 | 플랫폼 정책 확인이 먼저 필요 |

**추천**: 먼저 **C로 플랫폼 정책을 확인**하고, 백그라운드 신호가 필요하면 **A(포그라운드 서비스)**로 갑니다.

### A를 고르면 필요한 것
- 서비스 클래스: 흐름, 신호 구독, 차 제어를 서비스가 소유
- `AndroidManifest.xml`에 서비스 등록과 권한 추가
- 알림 채널과 알림(예: "맞이 진행 중")
- 화면은 서비스의 상태를 보여 주는 역할만

## 5. 팀에 확인할 것

1. **저장 방식**: DataStore와 Room 중 어느 쪽인지 (C 결정, 추천: DataStore)

3. **백그라운드 방식**: 플랫폼 정책 확인 후 A(포그라운드 서비스)로 할지 (팀 결정, 빌드 설정 변경 포함)

5. **근희(B)**: 복원 후 "원래 상태로 되돌리기"를 여러 번 불러도 안전한지 확인 부탁드립니다.
6. **이현(E)**: 복원 때 음성을 다시 재생하지 않는 것이 맞는지 확인 부탁드립니다.
7. **원영(D)**: 맞이 중에 탑승자 정보가 바뀌면(이름, 인사) 복원 때 어떤 값을 쓸지 정해 주세요.

## 8. Room 테이블 설계 (저장 방식 결정: Room)

> 프로젝트는 이미 Room을 쓰고 있어요(탑승자 저장, `ProfileDatabase`). 새 라이브러리 없이 맞이 상태만 저장해요.

### 8.1 DB 파일을 어디에 둘지 (중요)
- 기존 `maji-profile.db`는 `fallbackToDestructiveMigration()`을 써요.
  **같은 DB에 표를 추가하면서 버전을 올리면 탑승자 데이터가 전부 지워져요.**
- 그래서 **맞이 상태는 별도 DB 파일(`maji-flow.db`)로 나눠요.** 버전을 올려도 탑승자 데이터는 안전해요.
- 대안: 같은 DB에 넣고 `Migration(1, 2)`을 직접 만들면 가능하지만, 실수하면 데이터가 지워지므로 추천하지 않아요.

### 8.2 표 구조: `flow_snapshot` (한 줄만 씀)
| 칸 | 타입 | 뜻 |
|---|---|---|
| `id` | Int (고정 1) | 맞이는 하나만 있으므로 항상 1번 줄만 써요 |
| `step` | String | 단계 이름 (`MajiStep.name`) |
| `profileId` | Long | 탑승자 id |
| `season` | String | 맞이를 시작할 때 정한 계절 (`WINTER`/`SUMMER`). 자정에 달이 바뀌어도 학습은 이 계절로 가요 (원영 답변) |
| `savedSet` | Boolean | 바꾸기 전 상태를 읽었는지 (null과 구분) |
| `savedSeatHeat` | Int? | 바꾸기 전 열선 |
| `savedTemp` | Float? | 바꾸기 전 온도 |
| `savedWindow` | Int? | 바꾸기 전 창문 |
| `seatMovedMs` | Int | 원래 위치에서 움직인 누적 시간 (+ 앞, - 뒤). 취소·하차 때 반대로 움직여 되돌려요 (근희 B 제안, 결정: 저장함) |
| `preparedSet` | Boolean | 준비 값이 생겼는지 (아직 준비 전과 구분) |
| `preparedSeatHeat` | Int? | 준비 때 보낸 열선 (학습 기준) |
| `preparedTemp` | Float? | 준비 때 보낸 온도 (학습 기준) |
| `savedAtMillis` | Long | 저장 시각 (복원 기간 판단) |

- `Boolean` 칸을 둔 이유: `profiles` 표와 같은 방식이에요. "값이 없음(null)"과 "준비하지 않음"을 구분하기 위해서예요.
- **학습 후보(탑승 중 바뀐 열선·온도)는 넣지 않아요.** 팀 결정 6번(허용 여부)에 따라 나중에 추가할 수 있어요.

### 8.3 DAO와 저장소 (흐름 쪽)
- `FlowSnapshotDao`
  - `upsert(entity)`: 한 줄을 넣거나 바꿔요 (`@Insert(onConflict = REPLACE)`)
  - `get()`: 1번 줄을 읽어요 (없으면 null)
  - `clear()`: 1번 줄을 지워요
- `RoomFlowStateStore : FlowStateStore`
  - 흐름의 `save/clear`는 동기 함수라서, 실제 쓰기는 흐름의 `scope`에서 비동기로 해요.
  - 앱을 켤 때 `get()`을 한 번 읽어서 복원을 시도해요(복원 규칙은 3번 그대로).

### 8.4 버전과 마이그레이션
- 새 DB(`maji-flow.db`)는 **version = 1**로 시작해요. 이후 칸을 바꿀 때만 올리고, 그때는 Migration을 직접 써요(이 DB에는 탑승자 데이터가 없어서 destructive 방식도 허용 가능하지만, 복원 대상인 맞이 상태만 지워져요).
- `exportSchema = false`는 기존 DB와 맞춰요.

### 8.5 복원 기간 확인
- 읽은 뒤 `now - savedAtMillis`가 복원 기간(임시 하루)을 넘으면 버리고 `clear()` 해요.

### 8.6 팀 결정에 따라 남은 것
- 6번(학습 값 허용 여부): 허용 안 하면 지금 설계 그대로. 허용하면 `learnedHeat`, `learnedTemp` 칸을 추가해요.
- 백그라운드(5번): Room 설계와는 별개예요.

### 8.7 시트 이동 기록 (결정: 저장함)
- 차에서는 시트 위치를 읽을 수 없어서, 움직인 시간을 기록해 두고 되돌려요.
- 근희가 "시트 움직인 시간"을 메모리에만 두고 있어서, 앱이 꺼지면 사라져요. 그래서 `flow_snapshot`에 `seatMovedMs` 칸을 추가하고, 근희가 저장과 불러오기를 맞춰요.
- 이 기록이 없으면 재시작 후에는 시트를 원위치로 되돌릴 수 없어요(열선·온도·창문만 복원).

### 8.8 복원 규칙 (팀 답변 반영)
- **탑승자 정보**: 복원할 때 DB 최신 값을 읽어요(`profiles.get(profileId)`). 맞이 중 자리 설정 저장, 오늘만의 인사 비우기처럼 일부러 저장한 변경은 반영돼요 (원영).
- **탑승자가 삭제된 경우**: `get`이 null이면 맞이 시작 때 들고 있던 값으로 마무리하고, 학습(`learn`)만 건너뛰어요 (원영).
- **계절**: 맞이를 시작할 때 정한 계절(`season`)을 그대로 써요 (원영).
- **차 원래 상태 복구**: 탑승자 정보와 상관없이 `PassengerState`와 시트 이동 기록(`seatMovedMs`)으로 돌려요 (원영, 근희).
- **음성**: 복원할 때 인사, 안내음, 노래는 다시 재생하지 않아요 (이현).
- **차 상태 값**: 앱을 다시 켜면 기어와 문 값이 바로 들어와요 (나경). 그래서 차 상태 우선 규칙을 그대로 써요.
- **복구 반복**: 복구를 여러 번 불러도 안전해야 해요 (근희 확인 예정, 근희 작업).
